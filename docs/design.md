# 設計

ポコテンのネット対戦(mesaka/pokoten の `SPEC.md` 2.8)の「流れ」を、ゲームに依存しない土台として切り出す。
決定事項は `README.md`。ここでは構成と設計の理由をまとめる。

## 1. 現在のコードの、共通部分とゲーム固有の部分(ポコテン側)

| 部分 | 共通 | ゲーム固有(ポコテン) |
|---|---|---|
| `server/lobby_core.js` | 接続ID・登録・ランダム/ルーム・パスワード・準備OK/開始・一時停止の中継・チャット・再戦・退出 | `attack` `snap` `over` の中身・盤面の形式チェック・組み合わせの条件(むずかしさ) |
| `netplay.py` | `NetSession` の状態機械・時間切れ・チャット・`TextField`・文字の整形 | `attack()` `snap()` `lose()`・盤面の符号化・岩 |
| `nettransport.py` | WebSocket(ブラウザ/PC)・画面に重ねる入力欄・コピー・保存 | なし |
| `main.py` の `Net` | 画面遷移・テンキー・入力欄の同期・準備OK・一時停止・チャット窓・退出 | `Game` の生成と更新・右の列の描画・勝敗の効果音 |
| `ui.py` の net 系 | 名前・ルーム・待機・テンキー・チャット窓の画面 | 右の列(相手の盤面など) |

## 2. 構成

```
netgame_fw/

    worker.js                入口。createGameWorker(adapters) で、ゲームごとに組み立てる

  client/

      transport.py           WebSocket(ブラウザ=JS橋渡し / PC=websockets)
      session.py             NetSession(N人対応の状態機械。realtime / turns の両方)
      text.py                TextField・文字の整形・字形の判定(has_glyph)
      webinput.py            画面に重ねるブラウザ入力欄
      flow.py                画面の流れを動かす NetGameScene(アダプターを受け取る)
```

## 3. 設計の要点

### 3.1 N人対応の部屋モデル(将来の拡張を妨げない)
- 部屋は `players[]`(席 `seat` = 0,1,2…)・`state`・`config`(`min_players` / `max_players` / `match_key` / `mode`)を持つ。
- 「相手 `opp`」を前提にした名前を、「他の人たち」に一般化する。`match` は、自分の席 `you` と名簿 `players` を渡す。
- 結果は、勝敗ではなく**順位の配列**(`ranks`)で表す(2人でも同じ。勝ち=1位、負け=2位、引き分け=両方1位)。
- 一時停止は、**誰か1人でも止めたら全員止まる**(止めている席の集合で管理)。
- v1 の対象は 2人(`min_players = max_players = 2`)。3人以上の開始方法・退出時の扱い(`forfeit` / `continue` / `abort`)は、将来の拡張として、プロトコルに**席と名簿の形だけ**用意しておく。

### 3.2 2つの方式(realtime / turns)
- **realtime**: 各自が自分のゲームを計算する。ゲームは、サーバーに登録した種類のイベントだけを、他の人に中継できる。結果は、ゲームが申告(`finish`)して、サーバー側のアダプターが検証・確定する。
- **turns(ロックステップ)**: サーバーが `seed` と**手番**を持つ。手番の人だけが `action`(手)を送れる。サーバーは、通し番号 `seq` を付けて、全員に同じ順で配る。ルールはクライアントだけにあり、全員が同じ手の列から同じ状態を再現する。各自が、手を適用したあとの**状態のハッシュ**を送り、サーバーが突き合わせてずれを検出する。
- どちらも、準備OK・一時停止・チャット・結果・再戦・退出は共通。

### 3.3 サーバーの構成
- **(M1 の実装は、まず1つの `Hub` Durable Object。部屋の記録は DO のストレージ kv。)** 規模が必要になったら、組み合わせ用の `Lobby`(1つ)と、部屋ごとの `Room`(対戦ごとに1つの Durable Object)に分ける。部屋の状態は DO のストレージに持つ(ソケットの付属情報の2KB制限を避ける。ターン制の手の記録にも使う)。
- 接続先 `/ws?game=<id>&v=1` で、サーバーが、ゲームのアダプターを選ぶ。1つの Worker で、複数のゲームを動かせる。
- プロトコルに版 `v` を入れて、クライアントとサーバーの食い違いを検出する。
- ブランチのプレビューでは、Durable Object のバインディングを `previews` にも書く(`wrangler.jsonc` のテンプレートとして置く)。

### 3.4 ゲームとのつなぎ方
ゲームは、アダプターだけを書く。詳細は `adapter.md`。
- サーバー側(JS): 組み合わせの条件、中継してよいイベントと形式チェック(realtime)、手の検証(turns・任意)、結果の確定。
- クライアント側(Python): `GameAdapter` を継承して、フックを書く。`NetGameScene(adapter)` が、画面の流れを全部動かす。

### 3.5 画面部品
- 配色・文言・座標を、`Theme` / `Strings` で差し替えられるようにする。既定はポコテンの見た目。画面サイズ(いまは 480×800 固定の座標)は、ゲーム側の解像度に合わせて配置を計算する。
- 含めるもの: 名前入力、相手の決め方、ルーム(ルームID・パスワード・テンキー・コピー)、待機、準備OK、カウントダウン、チャット窓(テンプレート+自由入力)、結果、退出、「相手が退出しました」。
- チャットのテンプレートと、場面ごとの選択済みの規則は、ゲーム側が渡す。
- フォント: 軽量フォントの作成ツールを共通化する(ゲームの文言 + フレームワークの文言)。字形のない文字を通さない判定 `has_glyph` を入れる(`metrics()` は字形がなくても None を返さず、大きさ0の枠を返す)。

### 3.6 pygbag の制約(フレームワークの中で吸収する)
- Python の日本語の文字列を、そのまま JS に渡すと文字化けする → ASCII の JSON で受け渡す(入力欄・保存・コピーも同じ)。
- JS 側の名前の先頭を `__` にしない(Python のクラス内で名前が書き換わる)。
- `websockets` など、ブラウザで使えないモジュールは、文字列の `import_module` で読む(pygbag のビルドが探しに行かないように)。
- スレッドは PC 版だけ。ブラウザ版は、JS の WebSocket を毎フレームポーリングする。
- 画面に重ねる入力欄は、キー入力・マウスを `stopPropagation` して、ゲーム側(SDL)に取らせない。変換中(IME)は、中身を書き換えない。
- pygbag はアプリのフォルダ内のファイルだけを梱包する → 取り込みは、コピー(`git subtree` / 同期スクリプト)にする。

## 4. 主なリスク
- N人対応にすると、2人の「勝ち・負け」の前提が崩れる(順位・同時決着・途中退出)。結果を順位の配列にして備える。
- 画面部品の汎用化(解像度・配色・文言)は手間がかかる。最初は「ポコテンの見た目 + 最低限の差し替え」から始める。
- ターン制のロックステップは、ルールが**完全に決定的**であることが前提(乱数は seed 由来だけ。浮動小数・辞書の順序・並べ替えの安定性に注意)。ずれの検出で守る。
- 手札などの隠し情報は v1 では守れない。必要になったら、v2(サーバー権威型: `apply(state, seat, action)` を JS で書き、`view(state, seat)` で席ごとの見える範囲を切る)を先に作る。
- Cloudflare の Durable Object の無料枠・同時接続数。部屋ごとの DO にすると、リクエスト数が増える。
- 自動退出などの時間の判定は、いまはクライアントが行っている(切断で、サーバーが相手に通知する)。サーバー側のタイマー(DO のアラーム)が必要になるかもしれない(ターン制の持ち時間など)。
